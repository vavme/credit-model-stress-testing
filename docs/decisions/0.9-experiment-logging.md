# 0.9 — Experiment Logging

**Phase:** 0 (Scope Lock & Setup)
**Tag:** [You]
**Status:** Done
**Decided:** 2026-09-13

## The decision

A single flat results table (CSV or parquet) — one row per run. No MLflow, no Weights & Biases.

## Why

The point of this project is the result — the shape of the complexity premium as data quality degrades — not the infrastructure used to produce it. MLflow/W&B solve problems this project doesn't have: many collaborators, long-running production training jobs, dozens of hyperparameters to track. At 24 runs (3 corruption types × 4 severities × 2 models, per the locked scenario grid), a flat table is not just sufficient, it's more legible — anyone reading the repo can open one CSV and see every run and every metric, instead of needing to know an experiment-tracking UI. Extra infrastructure here would be something to explain and justify in the write-up for no real benefit, the same reasoning that ruled out Hydra for 0.8.

## How it will be implemented (Phase 3-5, not now)

This lands under `src/eval/`, whose `__init__.py` already names "the flat results table" as something it owns — no new module needed, unlike 0.8.

1. One row per completed run, appended to `results.csv` (or `.parquet` if the flat-file size ever makes CSV painful — unlikely at 24 rows).
2. Columns: `run_id`, the `ExperimentConfig` fields from 0.8 (`corruption_type`, `severity`, `model_type`, `seed`), then the metrics that come out of that run — AUC, Gini, KS on the held-out split, plus whatever SHAP-stability metric Phase 6 defines.
3. `run_id` can be a short hash of the config (`dataclasses.asdict(config)` hashed) so the same config always produces the same id — useful for checking whether a run has already been done before re-running it.
4. This table is what Phase 7 (results: expected vs. actual) and the bootstrapped-CI comparisons read from directly — no separate export or reformatting step.
