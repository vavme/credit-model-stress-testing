# 0.8 Config Schema

**Phase:** 0 (Scope Lock & Setup)
**Tag:** [You]
**Status:** Done
**Decided:** 2026-09-13

## The decision

YAML + a Python dataclass. Not Hydra.

## Why

Hydra earns its complexity when a project has many interacting config groups (model architectures, dataset variants, optimizer families, multi-run sweeps with overrides) and needs its composition/override system to stay sane. This project has exactly four axes that ever vary, corruption type, severity, model type, seed, and a fixed grid over them (3 corruption types × 4 severities × 2 models, per the locked scenario and severity decisions). A dataclass with four fields covers that completely. Reaching for Hydra here would be infrastructure to explain and justify in the write-up for no real benefit, the same reasoning that ruled out MLflow/W&B for 0.9.

## How it will be implemented (Phase 3, not now)

This is a scope decision, not code: the actual implementation lands when Phase 3 needs it (items 3.3 and 3.5: implementing the corruption functions and generating the experiment grid). Laying out the plan now so nobody has to re-derive it later or retrofit it after ad hoc scripts already exist:

1. **Define the shape once.** A single `@dataclass`, call it `ExperimentConfig`, in a new module, `src/config.py`. Fields cover exactly the four axes: `corruption_type` (one of `"mnar_missingness"`, `"label_lag_noise"`, `"schema_drift"`, or `"none"` for the clean baseline), `severity` (`0.0` / `0.10` / `0.25` / `0.50`), `model_type` (`"baseline_lr"` or `"xgboost"`), and `seed` (`int`, fixed by 0.10). A dataclass gives type hints and autocomplete for free, and, unlike a plain dict, Python raises immediately on a typo'd or missing field at construction time instead of silently ignoring it.

2. **Keep `configs/example_experiment.yaml` as documentation, not a file-per-run.** With 3 × 4 × 2 = 24 runs in the full grid, hand-writing 24 YAML files would be its own kind of scope creep. The example YAML stays useful as a single, human-readable reference for the shape (what a config looks like, field names, valid values), actual run configs get generated programmatically by looping over the grid and constructing `ExperimentConfig` instances directly in code.

3. **A small loader for the cases that do read from YAML** (e.g. a one-off manual run, or reproducing someone else's config): `yaml.safe_load(path)` to get a dict, then `ExperimentConfig(**raw)` to construct the dataclass. If a field is missing or misspelled in the YAML, this fails loudly at load time rather than producing a config with a silently-wrong value.

4. **Feeds directly into 0.9.** Each `ExperimentConfig` instance is what gets logged as a row in the flat results table (see `docs/decisions/0.9-experiment-logging.md`), `dataclasses.asdict(config)` gives the row's config columns, so there's one source of truth for "what ran," not two representations that can drift apart.
