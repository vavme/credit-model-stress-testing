# 0.4 — Test-Set Plan

**Phase:** 0 (Scope Lock & Setup)
**Tag:** [You]
**Status:** Done
**Decided:** 2026-09-13

## The decision

Carve one stratified 60/20/20 train/val/test split out of `application_train.csv` — the only file this project ever touches. `application_test.csv` has no public labels (it exists purely for Kaggle's leaderboard) and is never used for evaluation, for any reason. The 20% test slice is set aside once and stays untouched until Phase 5.

## Why 60/20/20 specifically

Each of the three splits is doing a different job, and the ratio reflects that:

- **Train (60%, ~184K rows).** Just needs to be enough for both models — the WOE-binned logistic regression and XGBoost — to fit stably at 25-40 features. At this dataset's scale that's true well before 60%; there was no need to push training higher.
- **Validation (20%, ~61K rows).** This is the slice that gets looked at repeatedly — reviewing WOE bin edges in Phase 2, smoke-testing the pipeline in Phase 3, any model comparison in Phase 4. Anything reused that many times needs to be large enough that repeated peeking doesn't quietly overfit to it, and large enough that the ~8% default rate still leaves a meaningful number of positive cases (~4,900) to judge things by.
- **Test (20%, ~61K rows), held out completely.** This is the slice the whole hypothesis rides on. The project's definition of "worth it" (0.9's decision) is whether a bootstrapped confidence interval on the complexity premium excludes zero — and the width of that interval depends directly on how many test examples, and specifically how many positive-class examples (~4,900 at this size), go into computing it. A smaller test set would mean wider, less conclusive intervals at exactly the severities where the answer matters most.

## Why not skew more toward training (e.g. 80/10/10)

The usual reason to shrink val/test in favor of train is that data is scarce and every row spent on evaluation is a row the model doesn't get to learn from. That trade-off doesn't apply here: compute and data-hunger were already ruled out as constraints when XGBoost was chosen over a neural net (see the hypothesis's compute-cost correction in `docs/PROJECT_CONTEXT.md`), and at ~307K rows even 60% training data is far more than either model needs. With nothing to gain from a bigger training set and a real cost — wider, weaker confidence intervals — to a smaller test set, there's no reason to skew the split. 60/20/20 is the balance point: enough training data with room to spare, and val/test slices big enough to support everything built on top of them (bin review, pipeline checks, and the CI-based "worth it" test itself).
